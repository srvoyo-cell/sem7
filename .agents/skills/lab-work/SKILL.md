# Lab Work — лабораторные и практические работы

## 1. Основные принципы

Скилл предназначен для решения лабораторных и практических работ на Python с использованием **marimo**.

Обязательные правила:

- Все работы выполняются исключительно на Python.
- Используй marimo для всей реализации.
- Весь программный код конкретной работы должен находиться в одном marimo-ноутбуке.
- Не создавай дополнительные Python-модули.
- Строго выполняй требования задания и варианта пользователя.
- Приоритет — математическая корректность, простота и читаемость.
- Не усложняй код архитектурными абстракциями.
- Допускается дублирование кода ради читаемости.
- Не создавай автоматические тесты.
- Не создавай отчёты или вспомогательные функции для формирования отчётов.
- Не сохраняй графики, CSV, таблицы или другие артефакты.
- Все результаты отображай непосредственно в marimo.

## 5. Использование marimo

### 5.1. Общие требования

Каждая работа должна быть реализована как самостоятельный Python-файл, содержащий marimo-приложение.

Рекомендуемое имя:

`lab_N.py` — для лабораторной работы.

`practice_N.py` — для практической работы.

Вся реализация должна находиться внутри marimo.

Не создавай:

- `main.py`;
- дополнительные файлы с вычислениями;
- дополнительные файлы визуализации;
- отдельные модули с утилитами;
- отдельные скрипты запуска.

### 5.2. Структура marimo

Организуй ноутбук как последовательность логических этапов:

1. Импорт библиотек.
2. Исходные данные и параметры.
3. Определение необходимых функций.
4. Математические вычисления.
5. Представление результатов.
6. Визуализация, если она нужна по заданию.

Каждый этап должен находиться в логически подходящей ячейке.

Используй реактивную модель marimo.

Соблюдай правила зависимостей между ячейками.

Не переопределяй одни и те же глобальные переменные в разных ячейках.

Не создавай искусственные зависимости ради порядка выполнения.

Не используй избыточные интерактивные элементы.

Если параметры задания фиксированы, не требуется создавать интерфейс для их изменения.

### 5.3. Отображение результатов

Результаты должны быть доступны непосредственно в marimo.

Для вычисленных величин используй обычный вывод значений или подходящие средства отображения marimo.

Не создавай функции исключительно для форматирования отчётов.

Не создавай автоматически текстовые отчёты по лабораторной работе.

Не сохраняй результаты во внешние файлы.

## 6. Требования к коду

### 6.1. Читаемость

Пиши максимально простой и понятный код.

- Используй осмысленные имена переменных и функций.
- Предпочитай последовательные вычисления.
- Разделяй сложные вычисления на понятные этапы.
- Не создавай абстракции, которые не нужны для решения задачи.
- Не используй универсальные архитектурные решения для частного задания.
- Избегай преждевременной оптимизации.
- Допускай дублирование, если оно повышает читаемость.
- Используй комментарии только для пояснения неочевидной логики.

Не сокращай код ценой ухудшения понимания алгоритма.

### 6.2. Функциональный стиль

По умолчанию используй функциональный стиль.

- Организуй повторно используемые вычисления через функции.
- Передавай данные через аргументы.
- Возвращай результаты через `return`.
- Избегай глобального изменяемого состояния.
- Отделяй математические вычисления от отображения результатов.

Не используй ООП, если оно явно не требуется методическими материалами или пользователем.

Не создавай классы ради группировки функций.

При этом не нужно помещать каждую операцию в отдельную функцию. Простые последовательные вычисления могут выполняться непосредственно в ячейках marimo.

### 6.3. Полная типизация

Все пользовательские функции и переменные должны иметь явные аннотации типов, насколько это совместимо с Python и marimo.

Обязательно аннотируй:

- Аргументы функций.
- Возвращаемые значения.
- Локальные переменные.
- Переменные с числовыми результатами.
- Коллекции.
- Массивы и другие структуры данных.

Пример:

```python
def calculate_mean(values: list[float]) -> float:
    total: float = sum(values)
    count: int = len(values)
    mean: float = total / count

    return mean
```

Для NumPy используй подходящие типы из `numpy.typing`, когда это необходимо.

Не используй `Any` без обоснования.

Не подавляй ошибки типизации ради прохождения проверок.

Учитывай, что служебные конструкции marimo могут иметь собственные требования к типизации.

### 6.4. Docstring и математические формулы

Каждая пользовательская функция должна иметь docstring.

Docstring должен описывать:

- Назначение функции.
- Аргументы.
- Возвращаемый результат.
- Связь с математической постановкой, если она есть.

Если функция реализует формулу из предоставленных методических материалов, обязательно указывай её номер.

Пример:

```python
def calculate_value(x: float, coefficient: float) -> float:
    """Вычислить значение по формуле (1.4) из методических материалов.

    Args:
        x: Аргумент функции.
        coefficient: Коэффициент.

    Returns:
        Результат вычисления.
    """
    result: float = coefficient * x

    return result
```

Дополнительные требования:

- Указывай номера формул точно по методическим материалам.
- Если используются несколько формул, перечисляй их.
- Если формула не имеет номера, указывай её раздел или описание.
- Если формула была преобразована, объясняй преобразование.
- Если функция не связана с формулами методических материалов, ссылка не нужна.

Никогда не придумывай номера формул.

## 10. Проверка качества

После реализации обязательно выполни проверки.

### Ruff

```bash

```

Проверка форматирования:

```bash
uv run ruff format --check lab_N.py
```

```bash
uv run ruff format lab_N.py
```

### ty

```bash
uv run ty check lab_N.py
```

Заменяй `lab_N.py` на фактическое имя файла работы.

Проверяй именно исходный код текущей работы, не затрагивая другие лабораторные.

Не отключай проверки и не подавляй предупреждения без достаточного обоснования.
